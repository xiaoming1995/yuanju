## Context

后台用户页已显示累计查盘和现存排盘数；起盘明细页通过 `/admin/charts` 展示现存 `bazi_charts`，API 仅按邮箱与日期筛选。微信用户可以没有邮箱，因此邮箱搜索不能作为用户记录跳转的筛选依据。`DeleteChart` 当前硬删除命盘与衍生内容；90 天活动事件不足以承担长期历史。

## Goals / Non-Goals

**Goals:** 从指定用户直接进入查询历史列表；通过用户 UUID 精确筛选；已删除的查询保留时间与状态；保留分页和日期筛选；可返回全站列表。

**Non-Goals:** 恢复已删除命盘内容、改变普通用户删除后的数据可见性、保留游客与已注销账号的用户级历史。

## Decisions

- 使用 `/admin/charts?user_id=<uuid>` 深链接，用户列表的姓名和累计查盘数字进入该页，“用户详情”仍打开用户详情；详情补同一入口。URL 可刷新和复制，不含邮箱或命盘内容。
- 现有管理员列表 API 增加可选 `user_id`。Handler 校验 UUID 并返回 400；Repository 在计数与分页查询使用同一精确 ID 条件。原有无参数行为保持全站列表。
- 新增 `user_chart_query_history`：以命盘 UUID 为主键，关联用户，只保存查询时间，不以外键引用命盘。查询时通过命盘是否仍存在判断“已删除”，因此无需保留删除时间。迁移从现存命盘回填，并尽量从尚未过期的 `chart_created` 活动事件补回已删除记录；将用户累计计数至少校准至可验证的历史条数。迁移前已过期的事件无法补回。
- 创建命盘、累计计数和写查询历史在同一事务；删除命盘继续硬删除命盘及衍生数据，独立历史留下时间与状态。小程序账户合并时转移历史归属；删除账号时通过外键级联清除其历史。
- 起盘页从 URL 读取用户范围。用户范围内隐藏邮箱搜索，日期筛选及清除操作只影响日期；提供“查看全站”链接。指定用户时 API 从查询历史分页读取，现存记录可查看命盘详情，已删除记录只显示时间和状态；全站无筛选列表保持现存命盘视图。进入命盘详情与返回列表时保留用户范围。

## Risks / Trade-offs

- 迁移前已经过期的已删除查盘无法逐条恢复 → 页面说明老历史可能不完整，不伪造时间或记录。
- URL 指向不存在的 UUID 时显示空列表 → 保持管理员列表 API 的空结果行为，不扩大数据暴露。

## Migration Plan

新增 goose 迁移，在发布依赖历史表的新后端前执行。旧客户端无 `user_id` 请求保持兼容。回滚会删除新历史表及其记录，需先备份。

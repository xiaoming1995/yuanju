## Context

今日问事通过 `quota_charged`、北京时间日期与全局每日上限限制免费次数；请求与 AI Token 用量日志分离。用户管理列表已有逐行「用户详情」操作和 Admin JWT；现有管理员审计事件有清理周期，不能承担长期余额账本。

## Goals / Non-Goals

**Goals:** 在用户列表直接发放一次性、跨日保留的额外次数；免费额度优先；并发不透支；失败按原来源退回；所有余额变动可追溯。

**Non-Goals:** 支付、充值入口、用户主动购买、有效期、个人每日免费上限覆盖、任意扣减。

## Decisions

- 新建不可改写的 `today_question_credit_entries` 流水：`grant +N`、`spend -1`、`refund +1`，带用户、管理员、请求、原因、时间与发放幂等键。余额为该用户流水之和，不用 Token 用量或用户表计数列代替。
- 请求表加 `quota_source`，旧有 `quota_charged=true` 回填为 `daily`；新请求选择 `daily` 或 `credit`。每日免费已用只数 `quota_source=daily`，额外消费通过流水核算。
- 发放、预占和失败退回均在事务内获取同一用户级 PostgreSQL advisory lock。原先用户+日期锁改为用户级，避免跨日期并发重复消费同一余额；请求与扣减同事务写入。技术失败/超时写补偿 `refund`，以唯一请求键防重复。
- 管理员发放 API 要求 Admin JWT、目标用户存在、正整数 1—1000、非空原因与幂等 UUID；重复同一键返回首次发放结果。弹框显示目标身份和当前余额，提交期间禁用按钮。
- 消费顺序固定：北京时间当日免费额度未满则用免费；否则用额外余额；两者均为零才返回 429。`insufficient` 作为有效问事仍扣次。

## Risks / Trade-offs

- 超时后旧 AI 返回 → 已标为失败并退回；迟到完成不得二次扣减或覆盖记录。
- 管理员误发 → 弹框明确显示目标和数量并要求原因；本阶段不提供冲正操作，账本保留完整记录。
- 用户被删除 → 请求和额度随账号删除；已有管理员审计清理策略不作为余额依据。

## Migration Plan

顺序迁移新增来源列和流水表并回填已计费的免费请求；旧请求不追扣额外余额。部署后检查原每日额度行为、新发放与并发消费、失败退回；回滚前须确认额外余额处理策略，本变更不自动迁移到其他系统。

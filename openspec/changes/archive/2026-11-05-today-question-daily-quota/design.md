## Context

今日问事已有按用户、北京时间日期记录的请求表，另有 `system_settings` 存储后台动态配置。当前请求直接创建，没有每日限制；同一用户的并发请求可能同时进入 AI。

## Goals / Non-Goals

**Goals:** 默认每天一次，后台可改 N 次；数据库层保证并发不超额；失败退回；现有审查日志保持完整。

**Non-Goals:** 本次不实现充值、支付、赠送次数、跨日结转或用户级特殊额度。

## Decisions

- 在 `system_settings` 增加 `today_question_daily_limit=1`。每次创建请求时读取配置，不缓存；后台只允许 1—100 的整数。缺少配置时默认 1，损坏配置时拒绝创建，避免绕过限制。
- 请求表增加 `quota_charged`，迁移前记录默认 `false`，新请求为 `true`。计数只看同一用户、`question_date`、`quota_charged=true` 且状态非 `error` 的记录；`processing` 占位，防止并发穿透；`insufficient` 计次。
- 创建请求时在单事务内取用户与日期的 PostgreSQL advisory transaction lock，读取设置、计数、插入。超过配额返回专用错误与 HTTP 429，不发起 AI 调用。技术失败在完成请求的事务内把 `quota_charged` 清为 `false`，保留失败审查记录。
- 遇到超过十分钟的 `processing` 记录时，将其标为失败并退回额度，避免进程中断后当日永久占位。若迟到的旧调用试图完成，按已失效请求拒绝写入。
- 在现有今日问事管理页放「每日免费次数」配置，不另建通用设置页面。未来充值用独立余额变动账本；不会把 Token 数或每日免费次数配置当成已购余额。

## Risks / Trade-offs

- 后台调低 N 时已有用户可能立即达到上限 → 只阻止后续请求，不改写已完成记录。
- 同日失败请求的 AI Token 可能已经消耗 → 仍保留原用量日志与审查记录，用户额度退回。
- 处理超时的请求占位十分钟 → 第二次提交会提示次数用完；超时后可重试。

## Migration Plan

新增顺序迁移，为 `today_question_requests` 加计次列和索引，插入默认配置；既有记录不计入上线后的额度。部署后验证默认 1 次、后台调整为 N、并发与失败退回。回滚删除新配置和列，保留原请求审查记录。

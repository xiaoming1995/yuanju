## Context

专属问事请求表保存用户问题与最终状态，原有 `token_usage_logs` 保存 AI 用量与输入输出；当前两者没有关联且新表重复保存 Token 数字。历史两条调用只存在于旧用量表，但其输入中包含服务端结构化上下文。

## Goals / Non-Goals

**Goals:** 为新请求建立稳定的一对一关联，原 Token 日志是用量权威来源；迁移可解析的历史调用到同一管理列表，不臆造旧回答；保留日后按用户、北京日期计数的请求记录。

**Non-Goals:** 本次不实现每日 N 次、充值、支付或扣费规则；不改全站其他 AI 功能的计费方式。

## Decisions

- 给请求表增加可空且唯一的 `token_usage_id`，新请求在同一事务内写入共享 Token 日志并完成请求。无 AI 用量时不创建用量行。
- 后台列表/详情通过关联表读取 Token 和原始输入输出；请求表只在没有用量行时保存输入输出，以覆盖模型失败。已有快照列保留作兼容回退，不再为新请求重复写 Token 数字。
- 原有月度用量归档删除明细前，在同一事务中把关联调用的 Token 分类和输入输出复制到请求记录。共享日志存在时仍以它为准；删除后使用请求快照，保证问事审查记录可读。
- 迁移从旧 `call_type=today_question` 的 Token 输入中提取已存在的服务端 JSON，回填问事日期、类别和问题，标记 `legacy`。旧日志没有最终呈现结果，详情明确显示未知。
- 后续免费次数应按请求记录的 `user_id`、`question_date` 和状态定义计数；充值次数应另建不可覆盖的余额变动账本，避免把 Token 用量当用户额度。

## Risks / Trade-offs

- 旧输入格式不符的记录无法可靠回填 → 只处理能解析出服务端 JSON 的记录，不伪造字段。
- 月度汇总仍只按原有共享 Token 日志计数；删除后的问事明细保存在请求表中，后续需要单独确定这类审查记录的保留期。
- 费用是按当时 Provider 价格估算 → 在请求表保留当时费用快照，Token 数字仍来自用量日志。

## Migration Plan

新增顺序迁移 `00035`，增加关联列、历史状态并回填可解析的旧调用；部署后检查原 2 条是否出现在统一列表，再验证新请求只产生一条共享 Token 记录。

## Context

网页端通过邮箱/密码创建 `users`，JWT 的 `user_id` 关联命盘、报告和历史。小程序只有本地示例。现有 `users.email`、`password_hash` 为非空，多个用户查询和网页/后台展示假定邮箱存在；管理员注册路由公开。

## Goals / Non-Goals

**Goals:** 保留网页邮箱注册/登录协议与既有用户 ID；小程序使用微信身份登录或绑定已有网页账号；两端共享同一普通用户权限和历史；小程序真实查询/历史/我的不显示固定命盘为真人结果；关闭公开管理员注册。

**Non-Goals:** 自动合并已分别创建且有数据的两个用户；AI 报告、微信支付、完整个人择日算法、生产域名及密钥的自动配置。

## Decisions

1. `users` 仍是唯一普通用户主体。迁移将 `email`、`password_hash` 放宽为可空，并增加约束：二者同时存在或同时为空。新建 `wechat_user_identities(app_id, open_id, user_id)`，`(app_id,open_id)` 唯一。旧行不改 ID、邮箱或密码哈希。`source` 仅记录初始来源，当前登录方式由身份关联决定。与另建微信用户主表相比，这保留所有 `user_id` 外键。
2. 网页邮箱 API 保留原路径与响应字段。读取无邮箱用户时仍以 `email: ""` 返回，避免现有 TS 运行时契约突变；网页/后台对空邮箱显示微信用户标识并禁用重置密码。已有邮箱用户的展示完全保持。后续如增加已验证邮箱流程再设计微信用户的网页密码设置，本次不允许认领未经验证的邮箱。
3. 小程序 `wx.login` 的 code 仅发给后端。后端从配置读取 AppID/AppSecret，经超时受控的 HTTPS 客户端调用微信 `jscode2session`，只使用 OpenID 识别账号，不返回 `session_key`。首次无映射时受独立 `miniapp_registration_enabled` 开关控制，数据库事务创建用户/映射；重试和并发均返回同一用户。已有网页账号可先通过邮箱密码登录，再用有效普通用户 JWT 与新 code 调用绑定接口。已绑定其他用户的微信身份返回 409，不自动移动历史。
4. 所有端的普通用户 JWT 继续使用原 `user_id` 和密钥；后台 JWT 保持独立。鉴权检查账户禁用/删除状态，小程序 401 清本地登录态。小程序首次登录需用户主动触发；登录前仍可查看静态日历。网页注册开关只控制邮箱注册，小程序首次建号使用独立开关。
5. 小程序建立集中请求层。真实排盘补齐性别，使用后端现有计算参数和结果。游客查询须明确保存语义：小程序先要求登录再创建真实命盘；未登录时不调用会静默落库的 `calculate`。历史/我的使用现有鉴权接口，列表分页、详情及删除按实际返回状态展示。固定示例日历和个人择日仅保留在明确标注的演示入口，不将真实命盘输入演示规则。
6. 删除公开 `/api/admin/auth/register` 路由，首次管理员由本地受控命令初始化。现有管理员登录路径保持。

## Risks / Trade-offs

- [微信凭证/合法域名缺失] → 使用可注入的微信 code 交换接口与本地模拟测试；真机验收待真实 AppID、AppSecret、HTTPS 域名。
- [数据库新用户空邮箱导致 Scan 失败] → 所有按 ID、后台列表、统计及个人中心查询使用空值安全读取并覆盖回归测试。
- [跨端账户误合并] → 绑定要求网页登录态及未占用微信身份；双方已有账户拒绝自动合并。
- [微信接口短暂错误或并发] → 网络超时、错误码处理、唯一约束与事务重查；不记录 code/密钥。
- [管理员初始化失败] → 发布前通过 CLI 初始化并验证登录；回滚应用时新增表与空邮箱用户不可简单删除，旧版仅在新用户尚未产生时可安全回滚。

## Migration Plan

1. 部署兼容旧数据的迁移与后端，验证旧邮箱注册/登录和旧 JWT。
2. 初始化/验证管理员，关闭旧公开注册入口；配置微信凭证与小程序建号策略。
3. 部署小程序请求层与真实业务页面；用真实小程序 AppID 和 HTTPS 域名逐端验收。
4. 若需要回退小程序，仅回退小程序包并保留后端兼容层；有微信用户数据后不得回退到不支持空邮箱的旧后端。

## Open Questions

- 真实 AppID、AppSecret 与 HTTPS 域名由部署环境提供；缺少时本地只验证模拟微信交换与现有 API。

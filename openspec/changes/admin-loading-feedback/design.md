## Context

后台已有 `--admin-*` 浅色变量、`.admin-loading` 文案、通用 Button 的 spinner、Toast 和 ConfirmDialog。页面数据加载分别在各页面管理：数据概览与 AI 日志有未捕获的读取失败；用户筛选可并发请求；起盘、合盘等页面把失败留在控制台。后台路由使用懒加载，但现有路由占位沿用用户端样式。工作区中还有未提交的浅色后台和用户活动改动，实施应基于当前文件逐页核对。

## Goals / Non-Goals

**Goals:** 管理员能从页面判断正在加载、成功但无数据、请求失败、操作仍在执行；失败后能就地重试；连续筛选只显示最新条件的结果；反馈与后台视觉体系一致。

**Non-Goals:** 重做后台信息架构、业务逻辑、API 响应格式或用户端主题；引入 UI 框架或全局数据请求库；自动重试有副作用的操作。

## Decisions

1. **以请求区域为单位管理状态。** 列表、详情、概览统计及独立图表各自使用 `loading / success / empty / error` 状态。首次进入用与内容结构相近的轻量占位；切换筛选或分页时保留旧数据和容器尺寸，显示局部更新提示，避免整页跳动。失败显示可见原因和重试按钮，空数据只由成功的空结果触发。沿用现有 `--admin-*` 变量定义共享样式或小组件，避免各页复制 CSS。相比整个后台遮罩，这不会阻断无关操作。

2. **操作反馈放在触发位置。** 保存、测试、启停、删除、清缓存等操作使用现有 Button 的 `loading` 或同等局部状态，提交期间禁用同一动作；成功与失败用现有 Toast 或表单内提示。危险操作仍使用既有确认流程。长耗时操作显示具体进行中动词；不因超时自动重发请求，避免重复写入。

3. **防止旧结果覆盖新选择。** 对筛选、分页、快速打开详情等可并发读取，用组件内请求序号或取消机制，只允许当前请求更新数据与状态。选择依据是当前 API 包装函数接口简单；先采用局部序号控制，若已有 AbortSignal 接口则复用。关闭详情或卸载后不再提交其结果。

4. **在请求层保留错误类别。** 将网络断开、超时、HTTP 错误转换为带类别的可展示错误，保留服务端已有 `{error}` 文案；401 继续既有登录跳转。页面可给出“连接超时，请重试”等准确提示。当前拦截器统一包装为 `Error('请求失败')`，需要调整时保持既有调用方 `instanceof Error` 可用。

5. **动效克制且可访问。** 加载占位使用低对比度脉冲，遵守 `prefers-reduced-motion`；区域使用 `aria-busy`、状态/错误文本可由辅助技术读取，重试按钮可键盘聚焦。后台路由懒加载占位使用后台色板，并保持窄屏内容宽度。

## Risks / Trade-offs

- [大量后台路由状态实现不统一] → 先建立共享状态样式/组件，再按数据概览、用户、AI 日志、起盘、合盘的关键路径落地，逐页核查其余路由同类缺口。
- [保留旧数据可能被误认为当前筛选结果] → 更新期间明确标注“正在更新”，完成前不把旧数据标为新结果；失败时说明当前结果未更新。
- [请求超时不代表写操作未生效] → 写操作超时后提示“结果未确认，请刷新核对”，不提供自动重试。
- [现有未提交工作与页面改动交叉] → 实施前检查 diff，保留这些改动并针对重叠文件验证。

## Migration Plan

纯前端渐进式改动，无数据迁移。按关键页面实现并验证后检查其余后台路由；回退前端变更即可恢复原交互。

## Open Questions

无阻塞问题。占位的具体形状和文案可在实现时随现有卡片、表格布局细化。

## Context

`miniapp/` 是使用本地固定示例和打包日历数据的原生微信小程序原型。首页、日历、结果、每日参考、择日和我的页面已有多处 `navigateTo`、`switchTab` 与本地 `setData` 操作，尚无统一的忙碌状态。首页打开结果只是跳转到固定示例，择日最多同步分析 90 个日历日；网页端已有的 React 加载组件不适用于原生小程序。开发者工具中的页面切换和真机首次渲染耗时尚未实测。

## Goals / Non-Goals

**Goals:** 每次跨页操作都立即得到可见反馈，等待较长时再展示状态；避免重复导航；在成功、失败和返回时可靠清理状态；让较慢的内容呈现有稳定占位，并能区分加载、空结果和错误。

**Non-Goals:** 不接入真实排盘、登录或网络请求；不人为延迟本地结果；不为每次即时选日、切换标签或打开弹层强行显示转圈；不引入 UI 依赖。

## Decisions

### 按等待来源分层反馈

所有可点击入口先提供按压态。跨页入口在点击后立即进入防重复点击状态；如果目标页面尚未可见且等待超过约 200 毫秒，再显示与入口相关的“正在打开…”提示。目标页就绪、导航失败或返回源页时清理状态。相比每次点击都弹出全屏加载层，这能让快速跳转保持轻快，也不会把固定示例误称为正在计算。

### 跨页状态由公共导航协调器管理

抽取仅服务小程序的轻量导航协调逻辑，用一次性标识关联入口和目标页。公共逻辑负责延迟提示、重复点击保护、导航失败回收和超时兜底；页面仍决定自己的文案与目标路径。首次进入页面和切换已存在的 Tab 分别由目标页面可见／就绪时机完成确认。相比各页面各写计时器，这能避免旧计时器在下一页弹出加载层。实现时要在开发者工具和真机核对微信页面生命周期，不把导航 API 的成功回调直接等同于内容已渲染。

### 本地更新优先保持即时响应

首页标签、日期选择、演示登录等本地状态更新仅使用选中态或操作反馈。择日范围更新先测量最长 90 天在目标设备上的计算与渲染耗时；若可感知等待来自批量计算或 `setData`，再把工作分段或让出绘制时机，并在结果区域显示局部状态。同步函数前后立即切换布尔 `loading` 不作为方案，因为同一轮事件内提示可能根本无法绘制。

### 页面占位只覆盖真实的首次呈现等待

在目标页可见但主要内容尚未就绪的路径使用卡片形状的轻量骨架和“正在加载页面”文字；显示条件由实际就绪状态决定，快速完成则不闪现。空结果和失败使用独立文案，失败后允许重试。占位沿用现有白卡、浅金底和深金文字，不新增位图素材或通用遮罩动画。

## Risks / Trade-offs

- [仅在开发者工具顺畅、真机仍慢] → 同时记录冷启动与再次进入的手机耗时，按实际慢路径验收。
- [导航生命周期提前回收或漏回收] → 覆盖 `navigateTo`、`switchTab`、返回、失败和超时；使用一次性标识阻止旧计时器影响新页面。
- [加载提示闪烁或遮挡内容] → 延迟显示短暂等待提示，优先在按钮或局部区域反馈，避免全屏遮挡。
- [同步计算阻止动画绘制] → 先测量并在必要时分段更新，不用人为等待伪造计算过程。

## Migration Plan

先覆盖共享入口反馈，再按实测慢路径增加目标页占位和择日局部状态；保留原有静态数据与业务结论。撤销此变更的页面状态、公共导航逻辑和 WXSS 即可回退，无数据迁移。

## Open Questions

目标真机上的冷进入与再次进入耗时、开发者工具是否能稳定复现等待，需在实现阶段测量；这些数据决定哪些目标页实际显示骨架。

## Context

`miniapp/` 是不调用后端的原生微信小程序原型。首页可选择任意生日，但结果页只展示固定命盘；择日页一次最多渲染 90 张完整日期卡；首页和我的分别持有历史副本。需要在保留原型可体验性的前提下，让动作、结论和数据来源一致。

## Goals / Non-Goals

**Goals:** 减少示例被误认为真实计算或择日推荐的风险；保持所有日期可追溯；同步演示历史；改善窄屏可读性和可点性。

**Non-Goals:** 不接入真实排盘、登录、持久化、完整择日规则；不重做页面架构或引入 UI 依赖。

## Decisions

### 查询原型明确使用固定示例

保留日期选择和独立结果页用于验证流程，但首页主按钮改为查看固定示例，结果标题直接标明示例生辰和本次日期未计算。日期选择只到小时，和当前后端契约一致；原型不增加性别、地点字段，直到真实排盘范围确定。相比删除日期控件，此方案仍能检验输入和返回状态。

### 择日结果强调依据，并按需展示

分组算法保持不变，仅更换面向用户的名称与摘要，避免暗示完整适宜性。每组首次显示最多七天，使用“显示更多”逐次增加七天；全范围日期始终可访问。切换事项或范围时重置展开量，避免旧列表状态干扰。相比一次只显示某一组，这种做法不会藏起冲突日期。

### 演示历史使用应用内单一状态

将历史副本放在 `App.globalData`，首页删除时更新，首页与我的在 `onShow` 时读取。它仍只存于当前进程，重启后恢复示例。相比引入本地存储，此方式吻合现有“临时移除”的文案。

### 用现有 WXSS 调整可读性

优先提高功能性说明、日期、状态、标签和按钮文字的字号及对比度，保留金色主视觉；扩大月切换与今日按钮的点击盒。基本排盘保持四列结构，手机画面须单独核对折行和横向溢出。

## Risks / Trade-offs

- [固定示例仍可能被误读] → 首页动作与结果首屏反复指明固定示例，正式版再接真实计算。
- [长列表展开后仍然较长] → 默认分段呈现，并允许逐段查看更多，不牺牲完整性。
- [字体放大会改变布局] → 运行静态检查和现有测试，尽可能在开发者工具模拟器核对窄屏。
- [进程内历史与真实账号模型不同] → 仅将此状态用于原型，不把它作为正式持久化方案。

## Migration Plan

原型代码本地替换，无数据库迁移；撤销本次小程序文件改动即可回退。

## Open Questions

真实版是否要把“查日期干支”和“排个人命盘”作为两个入口，需在接后端前确定。

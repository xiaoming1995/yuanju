## Context

后台用户列表由 `ListAdminUsers` 分页提供注册来源、状态和记录数，没有登录或活跃字段。网页邮箱与微信小程序均签发普通用户 JWT；小程序绑定网页账号会复用邮箱密码校验，不能把服务层每次校验都算作网页登录。起盘、合盘和 AI 用量已有独立业务表。数据库使用 goose SQL 迁移，后台鉴权在 Gin context 中提供 `admin_id`。

## Goals / Non-Goals

**Goals:**
- 准确记录成功认证与有限的核心行为，让管理员按用户查看和筛选。
- 管理员账号操作可追溯到操作者，事件内容保持最小化。
- 对旧数据、删除与小程序账号合并有确定的处理方式。

**Non-Goals:**
- 全站点击流、页面浏览、实时在线状态、跨设备会话管理与登录失败风控。
- 回填无法证明的历史登录时间，或复制命盘、报告正文到活动表。
- 在本次变更中改动用户端认证协议或引入分析服务。

## Decisions

### 1. 两种事件表与列表快照

新增 `user_activity_events`（`user_id` 外键 `ON DELETE CASCADE`、事件类型、渠道、可空的关联对象 ID、`created_at`）和独立的 `admin_user_audit_events`（管理员 ID、目标用户 ID 值、动作、时间）。事件类型和渠道使用服务端白名单，不允许客户端任意上报或自由格式元数据。`users` 增加可空的 `last_login_at`、`last_login_channel`、`last_active_at`，与相应事件在同一数据库事务更新，供分页筛选与排序。活动时间定义为最后一个成功的登录、注册或被追踪的业务行为时间；后台操作不改变用户活跃时间。事件流保留历史，快照提供高效列表查询。

替代方案是只查询现有业务表，或每次列表查询聚合事件。前者无法表示登录和资料更新，后者随着用户及事件量增长会使分页筛选昂贵。

### 2. 在成功边界采集

邮箱登录、微信登录分别在成功签发凭证的对外入口记录 `login` 及 `web`/`miniapp` 渠道；邮箱注册和微信首次建号记录 `register`，首次微信登录同时记录一次 `login`。绑定网页账号记录 `account_linked`，不得把内部密码校验记成网页登录。成功创建的起盘与合盘、成功生成并持久化的主八字或合盘 AI 报告、成功修改昵称或头像分别记事件；缓存读取、失败请求和重试前的处理中状态不记成功事件。业务写入与事件及快照更新尽量用同一事务；流式 AI 仅在服务端确认结果持久化后记成功。

替代方案是前端埋点，但客户端事件可丢失或伪造，也难与数据库成功提交一致。

### 3. 后台读取与操作审计

扩展现有 `GET /api/admin/users` 的可选筛选和排序参数，保留现有默认分页与搜索语义；新增 `GET /api/admin/users/:id` 和 `GET /api/admin/users/:id/events`。详情返回账号基础信息、可从现有表汇总的统计和分页事件，不返回出生数据、报告正文或密码散列。前端列表以本地时区格式化时间，详情用独立页面或抽屉展示；无时间值明确显示“从未登录”或“暂无记录”。所有接口沿用 Admin JWT 守卫。

管理员创建、禁用、解禁、重置密码和删除用户，在操作成功的同一事务写 `admin_user_audit_events`；无效目标返回 404，不写成功审计。删除后审计只保留目标 UUID、动作、管理员 ID 与时间，不保留邮箱或昵称；用户活动随用户删除。用户详情只展示仍存在用户的管理员操作，删除审计供后台审计查询或日志核查。

### 4. 保留与账号合并

用户活动明细保留 90 天，管理员操作审计保留 180 天，接入现有每日清理任务。`last_login_at` 和 `last_active_at` 是账号生命周期快照，不因明细过期而清空；UI 对此区分“最后时间”与“仅近 90 天可查看的明细”。小程序用户合并入网页账号时，在同一事务将活动事件改挂到最终账号，合并两个时间快照取较晚值，然后删除旧账号。旧用户不回填登录时间，历史业务记录也不伪造成新事件。

替代方案是永久保存活动明细；有限保留更符合排查与运营目的，也控制数据库增长。

## Risks / Trade-offs

- [业务写入成功但事件写入失败造成时间线缺口] → 核心写入与事件采用事务；难以合并事务的流式路径必须明确提交边界并对失败写入告警，不返回虚假的成功事件。
- [事件过多拖慢用户列表] → 列表只读 `users` 快照；事件按 `(user_id, created_at DESC)` 建索引并分页。
- [用户删除或账号合并造成错误归属] → 删除级联活动、独立保留最小管理员审计；合并事务内迁移事件和快照，并测试并发登录与合并。
- [敏感信息扩散] → 事件类型及关联字段白名单，管理员权限控制，不保存 IP、User-Agent、出生日期、请求体或报告内容。

## Migration Plan

1. 通过新 goose 迁移增加可空字段、两张事件表和必要索引；旧用户显示无记录。
2. 部署写入路径与后台读取路径；现有客户端接口响应不变。
3. 将两张事件表接入现有清理调度，并验证删除与合并场景。
4. 回滚应用时新字段和表可暂留，不影响旧版本；只有确认不再需要数据后才执行破坏性 down 迁移。

## Open Questions

- 90 天用户活动和 180 天管理员审计是本提案的默认保留期；正式上线前可按实际运营需要调整。
